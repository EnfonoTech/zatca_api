ZATCA API — Integration Guide

Create ERPNext Sales Invoices from any external system over REST, and get the ZATCA QR code back in the same response.

Base path /api/method/zatca_api.api.v1.  ·  Frappe/ERPNext v15  ·  ZATCA Phase 1 & Phase 2

What it does

One POST creates the invoice and returns the QR:

POST /api/method/zatca_api.api.v1.create_invoice
   → Customer / Address / Item / UOM resolved (idempotently)
   → Sales Invoice created and submitted
   → ksa_compliance signs it and files it with ZATCA
   → response: invoice detail + uuid, invoice_hash, QR content, QR PNG

Generic by design

No hardcoded credentials, fieldnames or defaults. Key names are matched case- and separator-insensitively, so an upstream system's own naming works without configuration.

Safe to retry

Your external_id is stored on an indexed field and locked on lookup. A repeat request returns the existing invoice instead of creating a duplicate.

No ZATCA crypto here

All TLV encoding, XML generation, hashing and signing is delegated to ksa_compliance. This app reads the result and shapes it for the response.

Ledger-safe

A submitted invoice is never rewritten. Taxes are computed by ERPNext, so mixed standard / zero-rated / exempt lines stay correct.

Prerequisite for ZATCA. Install and configure ksa_compliance on the site. It is an optional dependency: without it, invoice creation over REST still works and every response reports zatca.available = false.

Authentication

Standard Frappe token authentication. No endpoint allows anonymous access.

Generate a key pair in the desk: User → your integration user → Settings → API Access → Generate Keys. The secret is shown once.

Authorization: token <api_key>:<api_secret>

The user needs create, submit and read on Sales Invoice — nothing else. Accounts User is sufficient and is what we recommend: it grants exactly that. Every master this app creates on your behalf (Customer, Item, Address, UOM, Project) is written with elevated rights internally, so no role is needed for those. Permissions are checked against this user and are never escalated.

Do not give the integration user System Manager. A leaked key then stops being “someone can post invoices” and becomes “someone owns the site” — users, settings and all data. Verified: the full API surface works under Accounts User alone.

Never open that user in the desk and press Save. api_secret is a Password field, so the form loads it masked and saving writes the mask back, silently destroying the secret. Every request then fails with 401 AuthenticationError and the old value is unrecoverable. Change roles from the Role Profile or a script, and issue a new secret deliberately with bench --site <site> execute zatca_api.setup_test_site.rotate_api_secret, which is also the way to revoke a provider's access.

Optional extra guards

Under ZATCA API Settings → Security:

GuardEffect
Require Shared Secret Header Every request must also carry X-ZATCA-API-Secret (header name configurable). Compared in constant time.
Allowed IPs / CIDRs One IP or CIDR per line; blank allows any source. X-Forwarded-For is honoured left-most only.

Quick start

1. Confirm the install. Run this first whenever anything looks wrong — it reports whether authentication works, whether the custom fields are migrated, and which ZATCA phase each company resolves to.

curl -s -H "Authorization: token $API_KEY:$API_SECRET" \
  "https://<site>/api/method/zatca_api.api.v1.ping"

custom_fields_installed must be true. If not, run bench --site <site> migrate.

2. Create an invoice. There are two shapes, and tax_id is what separates them — not the customer's name, not a flag you set.

B2C — simplified

A consumer sale. No buyer VAT number, no address needed. Filed as 0200000 and reported to ZATCA after the fact.

curl -X POST "https://<site>/api/method/zatca_api.api.v1.create_invoice" \
  -H "Authorization: token $API_KEY:$API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "external_id": "POS-2026-0001",
    "customer": "Walk-in Customer",
    "company": "Enfono KSA",
    "items": [
      { "item_code": "SVC-01", "qty": 2, "rate": 350 }
    ]
  }'

B2B — standard

A sale to a registered business. The buyer VAT number makes it 0100000, cleared by ZATCA before you may issue it — and that in turn makes a complete buyer address mandatory.

curl -X POST "https://<site>/api/method/zatca_api.api.v1.create_invoice" \
  -H "Authorization: token $API_KEY:$API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "external_id": "INV-2026-0001",
    "customer": "Al Rajhi Trading Est",
    "company": "Enfono KSA",
    "tax_id": "300000000000003",
    "po_no": "PO-9931",
    "address_title": "Al Rajhi Trading Est Billing",
    "address_parts": {
      "street": "Olaya Street",
      "building_number": "4521",
      "district": "Al Murabba",
      "city": "Riyadh",
      "postal_code": "12613",
      "country": "Saudi Arabia"
    },
    "items": [
      { "item_code": "SVC-01", "qty": 4, "rate": 900 }
    ]
  }'

Omitting tax_id on a business sale is a compliance defect that throws no error. The invoice is accepted, the QR is returned, everything looks right — and it has been filed as a consumer sale. Check data.zatca.invoice_type_transaction: 0100000 means standard, 0200000 means simplified. If you sell to businesses, assert on that value in your own tests.

3. Read the QR from message.data.zatca, and poll get_status for the ZATCA filing outcome.

A ZATCA QR only exists for a submitted invoice. Keep Auto Submit Invoices on in ZATCA API Settings, or pass "submit": true. A draft returns zatca.available = false with a reason saying exactly that.

Dry run — test before you write anything

Give this endpoint to whoever is building the feed. Nothing is written to the database, so they can run it against the live site as often as they like while iterating.

POST /api/method/zatca_api.api.v1.validate_payload

Send exactly the invoice JSON you intend to send for real. Add ?document_type=Credit Note for a return.

Response keyWhat it tells you
valid The verdict. A 200 only means the check ran — always read this.
errors[]Every problem, each naming the exact field.
warnings[]Non-fatal; usually an incomplete buyer address.
totals The real ERPNext totals. Compare against your own figure — a mismatch means a tax or discount misunderstanding.
would_create Which Customer / Items / UOMs would be new. A large unexpected new_items means unstable item codes.
zatca.invoice_type Standard or Simplified, plus the reason.
zatca_readiness.blocking The things ZATCA will reject. Must be empty.

How it writes nothing yet gives real totals. The payload runs through the same code path as a real request, inside a database savepoint that is always rolled back — on every path, including an unexpected error. So the totals come from ERPNext's own calculation and the errors from ERPNext's and ksa_compliance's own validation, not from a parallel reimplementation that could drift and pass payloads which later fail. The invoice is inserted as a draft only, never submitted, so no ledger entry is written and nothing is filed with ZATCA.

Building the feed on the other side? Send them docs/DATA_CONTRACT.md rather than this page — it is written for them, with the ZATCA rule behind each field and a sign-off checklist. A JSON Schema and worked sample payloads ship alongside it in docs/schema/ and docs/samples/.

Response envelope

Frappe wraps every whitelisted return value in message, so the envelope sits one level down:

{
  "message": {
    "success": true,
    "request_id": "a1b2c3d4e5f6",
    "timestamp": "2026-08-04 11:30:00",
    "data":     { ... },
    "warnings": [],
    "errors":   []
  }
}

The shape is identical for success and failure, so one parser handles both.

  • request_id — correlation id, also stored on the request log. Quote it when reporting a problem.
  • warnings — non-fatal; the invoice was created. Most often buyer address parts that ZATCA will reject for a standard invoice. Log these.
  • errors[].code — branch on the code, never on the message text. Messages are translated.

The zatca block

data.zatca is always present. Check available first.

Phase 1 vs Phase 2

FieldPhase 1Phase 2
phasePhase 1Phase 2
qr_content null — the helper returns an image only base64 TLV string
qr_formatpng-only base64-tlv
qr_png_base64, qr_png_data_uri yes yes
uuid, invoice_hash, previous_invoice_hash, invoice_counter null — there is no filing yes
integration_statusNot Applicable ZATCA outcome — asynchronous

Timing — the one thing to get right. On submit, ksa_compliance signs the invoice locally. So the uuid, invoice_hash, previous_invoice_hash and the QR are already in the create response. Only integration_status moves asynchronously, because the clearance or reporting call to ZATCA runs in a background job.

Take the QR from the create response; poll get_status for the filing outcome. Do not hold the HTTP connection open waiting.

integration_status values

ValueFlagsMeaning
Ready For Batchpending Signed, not yet filed.
Acceptedcleared ZATCA accepted it.

When available is false

reason says why — usually the invoice is still in Draft, the company has no ZATCA settings, or ksa_compliance is not installed. Creating the invoice still succeeded in every one of those cases.

Short numeric building numbers and postal codes are zero-padded automatically (521 → 0521). Over-long or non-numeric values cannot be salvaged and are rejected.

Mandatory for B2B. If the buyer has a VAT registration number or another ZATCA identifier, an incomplete address is an error, not a warning — the request is rejected with a per-field list and nothing is created.

The rule comes from ksa_compliance: _set_buyer_details passes validate=True to _set_buyer_address whenever the invoice type is Standard, and throws outright when a B2B customer has no address at all. Catching it here gives the caller a precise message before any document exists.

For a B2C buyer the same gaps stay warnings — a simplified invoice needs no buyer address. Relax the behaviour with Require Complete Address For B2B only on a non-KSA site or during a legacy migration.

Taxes

Precedence:

  1. taxes array in the payload — used verbatim. Each account_head is validated to exist and belong to the invoice's company.
  2. tax_template — a named Sales Taxes and Charges Template for the company.
  3. The company's default template.
"taxes": [
  { "account_head": "VAT 15% - EK", "charge_type": "On Net Total",
    "rate": 15, "description": "VAT 15%" }
]

charge_type Actual takes tax_amount; every other type takes rate.

In all three cases the per-row item_tax_template governs which lines are taxed and at what rate, and ksa_compliance builds each line's VAT category from that same template — from its custom_zatca_item_tax_category, which supplies the S / Z / E / O code and the VATEX-SA-* exemption reason.

That holds where the site is configured so every template prices the same VAT account as the header tax row, no item master carries a conflicting template, and each template has its ZATCA category set. A template left blank silently files as standard.

Each VAT category needs its own item_code. ERPNext keys per-line tax detail by item code, so one code across two templates collapses them and ZATCA rejects the filing (BR-CO-14 / BR-CO-15).

Payment means — requires is_pos

ksa_compliance resolves the ZATCA payment means code from payments[0].mode_of_payment → Mode of Payment.custom_zatca_payment_means_code.

ERPNext, however, gates the Sales Invoice.payments table on eval:doc.is_pos===1, so on a regular invoice the row is silently discarded at insert and no payment means code is ever reported.

This app refuses rather than dropping it. Sending payment_mode without is_pos returns a validation_error naming the constraint. Send both when you genuinely want a POS invoice:

{ "payment_mode": "Cash", "is_pos": 1, "payment_amount": 230 }

is_pos: 1 makes it a POS invoice — ERPNext posts the paid amount against the mode of payment's account, so payment_amount changes the GL. Leave it off (defaults to 0) to declare the means without recording a receipt.

If no tax rows can be resolved and ZATCA is enabled for the company, the request is rejected with a specific message — ksa_compliance requires a non-empty taxes table. Set a default template for the company, or send taxes / tax_template on every request.

Idempotency

Every invoice stores your external_id in the indexed custom field Sales Invoice.zatca_api_external_id.

Existing invoiceResult
noneaction: "created"
Draft, Update Existing Drafts on action: "updated" — rewritten in place
Draft, Update Existing Drafts off action: "duplicate" — left untouched
Submitted action: "duplicate", duplicate: true — never re-posted
Cancelled 409 immutable_document — send a new id

The lookup takes a FOR UPDATE lock on the indexed column, so two concurrent requests carrying the same id serialise instead of racing to insert two invoices. Retrying is always safe — a network timeout where the server actually committed resolves cleanly.

Why not key on the invoice name? Because it cannot work. frappe.model.naming.set_new_name executes doc.name = None for any DocType with a naming series, which Sales Invoice has. Passing a name is silently discarded and the invoice is named ACC-SINV-YYYY-#####, so an existence check against your number never matches — and a repeating import creates a fresh duplicate on every run.

ZATCA Phase 2 checklist

Work through this before going live. ping reports items 1–3.

  1. ksa_compliance installed and configured. ZATCA Business Settings with status = Active and ZATCA integration enabled; CSR generated, production CSID obtained, zatca_cli_path and java_home set.
  2. Company address complete — street, building number, city, district, postal code.
  3. Company VAT registration number set (15 digits, starts and ends with 3).
  4. A default Sales Taxes and Charges Template, or send taxes / tax_template every time.
  5. Buyer identification for B2B — send tax_id, or buyer_id_type + buyer_id_value.
  6. Buyer address complete for standard invoices — send address_parts, or enable Parse Free-Text Address and send address_display.
  7. Auto Submit on. No submission means no QR.
  8. Reconcile. Poll get_status, or sweep list_invoices?integration_status=Rejected and refile with resubmit_to_zatca.

The one that bites. ksa_compliance.is_b2b_customer() reads Customer.custom_vat_registration_number and Customer.custom_additional_ids — not the core tax_id field. A customer with only tax_id populated is classified B2C, so a genuine B2B sale is reported as simplified instead of cleared as standard.

This app writes both fields, so sending tax_id is enough. But if you create customers by any other route, set custom_vat_registration_number yourself.

Free-text address parsing

When the source system only exports one address line, enable Parse Free-Text Address. The built-in patterns handle ERPNext's own KSA layout:

Building No 4521, Olaya Street, Al Murabba Dist, P.C: 12613, Riyadh, Kingdom of Saudi Arabia
  → street = Olaya Street        building_number = 4521
    district = Al Murabba Dist     postal_code = 12613     city = Riyadh

Variants are handled: Building No. with a dot, P.C without a colon, District spelled out, and KSA / Saudi Arabia / Kingdom of Saudi Arabia.

Override them in Address Parse Patterns, one field=regex per line — the first capture group supplies the value:

address_line1=Street:\s*([^,]+)
custom_building_number=Bldg\s*#?\s*(\d+)
pincode=ZIP\s*(\d{5})
custom_area=Area:\s*([^,]+)
city=City:\s*([^,]+)

Patterns are compiled when you save, so a bad regex is rejected then rather than breaking an invoice later. Explicit address_parts values always win over parsed ones.

Missing parts come back as warnings before ZATCA rejects the invoice:

"warnings": [
  "Buyer address has no building number (custom_building_number).",
  "Buyer postal code \"123\" is 3 characters; ZATCA requires exactly 5."
]

Custom field mapping

Nothing client-specific is hardcoded. To land an arbitrary payload key on any ERPNext field — including a custom field — add a row under ZATCA API Settings → Field Mapping:

Target DocTypeSource KeyTarget Field Value Type
Sales InvoiceMEASUREMENTDATE custom_measurement_dateDate
Sales InvoiceANNEXUREREFID custom_annexure_ref_idData
Sales Invoice ItemLINE_REF custom_line_refData
ProjectCONTROLVALUEINSAR custom_control_valueCurrency
  • Source Key uses the same case/separator-insensitive matching; dotted paths reach into nested objects.
  • Target Field is validated against the DocType meta when you save, so a typo is an error you see immediately rather than a value silently dropped.
  • Value Type coercion uses cint/flt/ getdate, which absorb null, "" and locale-formatted numbers like "1,250.00".
  • Mandatory rejects the whole request when the key is absent.

Supported targets: Sales Invoice, Sales Invoice Item, Customer, Item, Address, Project.

Pull mode (optional)

Use this only when the external system cannot POST into ERPNext. Push mode is preferred because it returns the QR synchronously.

Configure one row per upstream endpoint under ZATCA API Settings → Pull Sources, then tick Enable Scheduled Pull. A cron runs every 15 minutes and is a cheap no-op while disabled. Trigger one immediately with pull_now.

FieldNotes
Endpoint URLMust be http:// or https://.
Auth TypeNone, Header Key, Bearer Token, Basic.
Secret / API Key Encrypted at rest. Never echoed by any response, never in a git diff.
Payload Root Key Key holding the invoice array, e.g. payloads. Dotted paths work; blank means the body is the array.
Status Key / Status OK Value Optional envelope assertion before processing.
External ID KeyWhich key identifies the source document.
TimeoutSeconds; defaults to 30. Never unlimited.
Auto SubmitSubmit pulled invoices. Required for a QR.

Each invoice is committed in its own transaction, so a failure on invoice 40 leaves the first 39 durably imported and rolls back only the failed one. Dedup is by external id, so re-polling the same feed duplicates nothing.
