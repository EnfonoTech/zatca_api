ZATCA API — Integration Guide

For the team building the invoicing side. Send us an invoice, get back an ERPNext Sales Invoice and its ZATCA QR code.

Test endpoint https://zatca-test.enfonoerp.com  ·  every example on this page is a real captured request and response

The flow

Four steps. Steps 1 and 4 are optional but strongly recommended.

1. POST validate_payload   ->  we check your JSON, write nothing
                               iterate until valid = true

2. POST create_invoice     ->  we create AND submit the Sales Invoice
                               response already contains the ZATCA QR

3. store what we return    ->  invoice name + QR (put the QR on your PDF)

4. GET  get_status         ->  call back for ZATCA's verdict, which is
                               asynchronous on Phase 2 sites

One call does it

Step 2 creates, submits, signs and returns the QR in a single HTTP response. You do not need to poll to get the QR.

Retrying is safe

Send the same external_id again and you get the existing invoice back. Nothing is duplicated, ever.

Test before you build

validate_payload writes nothing to the database. Hammer it against the live test site while developing.

Only status is async

The QR, UUID and invoice hash are computed locally at submission. Only ZATCA's accept/reject arrives later.

Credentials

We issue you an API key pair. Send it on every request:

Authorization: token <api_key>:<api_secret>
Content-Type: application/json

Base path for every endpoint:

https://zatca-test.enfonoerp.com/api/method/zatca_api.api.v1.<endpoint>

There is no anonymous access. A request without a valid header gets 403. Keep the secret server-side — never in a mobile app, browser bundle or committed file.

1 · Validate — writes nothing

POST /api/method/zatca_api.api.v1.validate_payload

Send exactly the JSON you intend to send for real. We reply with every problem, the real totals we would produce, what master records would be created, and whether the invoice would file with ZATCA as standard or simplified.

The dry run validates creation, not submission. It inserts a draft and rolls it back, so a few checks that only run when accounting entries post can still fail on the real call. A clean dry run means your payload is right. If a real call fails after a clean dry run, tell us — that one is ours.

2 · Create the invoice

POST /api/method/zatca_api.api.v1.create_invoice

This creates and submits the Sales Invoice. Submission is what produces the ZATCA QR, so it happens in the same call.

Only send an invoice once it is final in your system. A submitted invoice cannot be edited, and once ZATCA has cleared it, it is legally immutable. Corrections happen by credit note — never by re-sending a changed invoice.

What to store

FieldWhy you need it

4 · Call back for ZATCA's verdict

GET /api/method/zatca_api.api.v1.get_status?external_id=YOUR-REFERENCE

You already have the QR from step 2. What you do not yet have is ZATCA's answer, because filing the invoice with ZATCA runs in a background job after the response has gone out.

So: take the QR from step 2, then call back here for the verdict.

What integration_status means

ValueMeaningYour action
Not ApplicablePhase 1 site — no filing step existsNothing. Done.
Ready For BatchSigned, not yet filedPoll again shortly
AcceptedZATCA accepted itNothing. Done.
Accepted with warningsAccepted; ZATCA raised warningsLog them
Clearance switched offFiling intentionally disabledNothing
RejectedZATCA refused itTell us. Needs a fix then a refile
ResendTransient failure (timeout, 5xx, rate limit)Poll again; we retry

Two booleans save you parsing the strings: is_pending (still waiting) and is_cleared (finished successfully).

Recommended polling

after create_invoice succeeds:
    if zatca.is_pending is false  ->  done, nothing to poll
    else:
        wait 30s, GET get_status
        repeat with backoff (30s, 1m, 2m, 5m) for up to ~15 minutes
        if still pending  ->  stop polling, flag for a human

Do not poll in a tight loop, and do not block your invoice workflow on the verdict. The customer's invoice is valid and printable with the QR you already hold.

Need the whole invoice back?

GET /api/method/zatca_api.api.v1.get_invoice?external_id=YOUR-REFERENCE

Same ZATCA block, plus every header, line and tax row. Add &include_xml=1 for the signed UBL XML on Phase 2 sites.

The Phase 2 model

Phase 2 is the production ZATCA model. Your payload does not change at all — everything in this guide applies unchanged. What changes is the zatca block you get back, and the fact that ZATCA's verdict becomes meaningful.

The examples earlier on this page were captured from a Phase 1 test site, so their uuid, invoice_hash and qr_content are null and integration_status is Not Applicable. This section documents what those same fields contain on a Phase 2 site. Build for both: read zatca.phase and branch.

The timing is the important part. Signing happens on our server the moment the invoice is submitted — no network call to ZATCA is involved. So uuid, invoice_hash, previous_invoice_hash and the QR are all in the create response, immediately, exactly as on Phase 1.

Only integration_status is asynchronous, because filing the invoice with ZATCA runs in a background job. That is the one field you call back for.

Clearance vs reporting

ZATCA treats the two invoice types differently, and this is decided by whether you sent a buyer identifier:

Standard (B2B)Simplified (B2C)
You sendtax_id or buyer_id_*neither
invoice_type_transaction01000000200000
ZATCA processCleared — before you issue it Reported — after the fact
Buyer addressMandatoryNot required
Practical effect A rejection means the invoice must not be issued as-is A rejection is a reporting failure to correct

The status lifecycle you must handle

create_invoice returns
        |
        v
integration_status = "Ready For Batch"      <- signed, QR valid, not yet filed
        |
        |  background job files it with ZATCA
        v
   +----+---------------------------+
   |                                |
"Accepted"                      "Rejected"
"Accepted with warnings"        "Resend"     <- transient; we retry
"Clearance switched off"
   |                                |
 done                       tell us / refile

Poll get_status exactly as described in step 4. Use the booleans rather than matching strings:

if zatca.is_pending:      keep polling with backoff
elif zatca.is_cleared:    done
else:                     Rejected or Resend - alert, do not silently ignore

If ZATCA rejects an invoice

Do not re-send it as a new invoice — that would duplicate it. The refile is done on our side:

POST /api/method/zatca_api.api.v1.resubmit_to_zatca
{ "external_id": "YOUR-REFERENCE" }

That routes through ksa_compliance's own retry, which keeps the invoice-hash chain intact. Re-signing outside it would corrupt the chain for every subsequent invoice, so never attempt a manual refile.

An already-accepted invoice is skipped rather than filed twice.

Rejections are usually a data problem, not a transport problem. The common causes are all things you control: a buyer VAT number that is not 15 digits starting and ending with 3, a building number that is not exactly 4 digits, a postal code that is not exactly 5, or a missing district. Run validate_payload first and zatca_readiness.blocking catches these before ZATCA ever sees them.

What you must do differently for Phase 2

  • Nothing for the QR. Same field, same base64 PNG, same place.
  • Store uuid and invoice_hash against your local record. They are ZATCA's identifiers for the invoice and you will want them in any dispute.
  • Actually poll get_status, and act on Rejected. On Phase 1 this step was a no-op; on Phase 2 ignoring it means silently unfiled invoices.
  • Prefer qr_content if you render the QR yourself. It is the raw TLV; do not re-encode our PNG.
  • Never send a corrected version of a cleared invoice. Issue a credit note.

ZATCA rules that will reject you

Standard vs simplified

Simplified (B2C)Standard (B2B)
BuyerConsumer, walk-inA registered business
Filed asReported after the factCleared before issue
Buyer VAT numberNot neededRequired
Buyer addressNot neededRequired, complete

The most expensive mistake in this integration. If you sell to businesses and omit tax_id, every invoice is filed as simplified. It will not error. It will look completely fine. It is a compliance defect, and it typically surfaces in an audit.

If the buyer is a business, send the VAT number.

Buyer address — enforced

Send a VAT number and these five become mandatory. We reject the request rather than let ZATCA reject the filing later.

FieldZATCA rule
streetNot blank
building_numberExactly 4 digits. 521 is invalid — send "0521"
districtNot blank
cityNot blank
postal_codeExactly 5 digits

Send building_number and postal_code as strings, not numbers, so leading zeros survive. And tax_id is 15 digits starting and ending with 3.

Mixed VAT rates

If any invoice can mix standard 15%, zero-rated exports and exempt items, you must send item_tax_template on every line. Otherwise all lines get the same rate and ZATCA receives the wrong per-line VAT category. We will give you the exact template names.

If every line is always standard 15%, omit it entirely.

Errors and retries

Same envelope shape whether it succeeded or failed, so one parser handles both. Branch on errors[0].code, never on the message text — messages are translated and may change.

Retrying — the important part

Network timeouts happen, and you cannot tell a lost request from a lost response. So always retry with the same external_id.

If your retry generates a new external_id, you create duplicate invoices, and duplicates require manual accounting cleanup. This is the single most important rule on this page.

A failed request is fully rolled back — it never leaves half-created customers or items behind.

Implementation outline

function send_invoice(local_invoice):

    payload = build_payload(local_invoice)
    # external_id MUST be your own stable document number
    payload.external_id = local_invoice.number

    # during development only
    check = POST validate_payload, payload
    assert check.data.valid and check.data.zatca_readiness.blocking is empty

    for attempt in 1..3:
        try:
            r = POST create_invoice, payload      # same payload every attempt
            break
        except timeout or 5xx:
            wait 2^attempt seconds               # never change external_id
            continue

    if not r.success:
        if r.errors[0].code == "validation_error":
            log and stop; a human must fix the data
        else:
            alert with r.request_id

    save local_invoice.erp_name  = r.data.invoice.invoice     # for credit notes
    save local_invoice.qr_base64 = r.data.zatca.qr_png_base64 # for the PDF
    save local_invoice.warnings  = r.warnings

    if r.data.zatca.is_pending:
        schedule_status_poll(payload.external_id)   # step 4, with backoff
